# 需求文档 Review 问题清单 — axhub-proto-enhanced

**Review 角色**：资深产品经理
**评审对象**：
- `openspec/changes/enhance-prototype-tool/proposal.md`
- `openspec/changes/enhance-prototype-tool/design.md`
- `openspec/changes/enhance-prototype-tool/tasks.md`（参考）

**评审维度**：需求完整性 / 用户价值 / 优先级

---

## 一、需求完整性问题

### 🔴 高

- **Q1. 缺少目标用户画像与使用场景定义**
  proposal.md 仅描述功能增强，未说明：谁会用这个增强版？是产品经理、UX 设计师还是开发？典型使用场景是什么（紧急改一版原型 vs 长期维护设计稿）？没有用户场景就无法判断功能取舍是否正确。

- **Q2. 缺少与非 fork 替代方案的对比论证**
  直接得出 "fork 更灵活"（design.md 决策 4），但未论证为何不选：(a) 给上游提 PR；(b) 写 plugin/中间层包装；(c) 基于其他成熟工具（Penpot、即时设计 API）。fork 维护成本极高，需要更硬的证据支撑。

- **Q3. "手动编辑画布" 需求边界不清**
  这是本变更最大、最复杂的模块，但 proposal 只有一句话（"支持拖拽式手动编辑组件属性、布局、样式"）。需澄清：
  - 是否支持撤销/重做？多选？复制粘贴？图层锁定？
  - 是否支持父子嵌套拖拽？响应式布局调整？
  - 编辑历史是否持久化？刷新页面后画布状态去哪？
  - 与 AI 再生成如何协同 —— AI 二次生成会覆盖手动修改吗？冲突解决策略？

- **Q4. 缺少数据持久化与项目模型定义**
  组件树是"单一数据源"，但没说明：
  - 项目如何保存？单文件 JSON？多文件目录？放用户哪里？
  - 支持多页面/多画板吗？（tasks.md 5.5 提到"批量导出多页面"暗示多页面，但 proposal/design 完全没提页面管理模型）
  - 是否支持版本快照/恢复？

- **Q5. 验收标准不可度量**
  "成功标准 5 条" 中：
  - "手动微调每个组件" —— "微调"无定义
  - "覆盖企业级常见组件（≥20 种）" —— 数字有了但"企业级常见"无清单
  - "保持同步能力" —— 没有可验证的指标（例如：merge 上游后核心功能仍通过 E2E 测试）
  - 缺少性能指标（首屏渲染时间、导出耗时上限、可编辑组件数上限）

### 🟡 中

- **Q6. Axure 兼容性矩阵缺失**
  说"所有组件导出到 Axure 后保持可编辑"，但未指明 Axure RP 的最低支持版本（8/9/10？）、不同版本间的字段差异如何处理。Axure 9 和 10 的 widget 模型有差异。

- **Q7. 图表/地图/富文本组件的"可编辑"定义不明**
  这类组件在 Axure 中没有原生 widget。导出后是变成矩形+文本拼合？还是转成 Axure 内嵌框架/Inline Frame？需要明确降级策略，否则 "可编辑" 这条标准无法兑现。

- **Q8. 错误处理与异常路径未定义**
  - AI 生成的组件树不规范（嵌套过深、组件未知）时怎么办？
  - Axure Bridge 未启动/版本不匹配时的用户引导？
  - HTML 导出外部资源（图片 CDN、字体）离线打开失败如何处理？

- **Q9. 上游同步机制的"冲突解决"过于乐观**
  tasks.md 7.2 只有一行 "解决首次 merge 冲突"。实际上一旦 fork 深度修改 `axhub-export-core`，每次 merge 都可能产生大量冲突。需要：(a) 明确禁止修改的核心文件清单；(b) 自动化冲突检测 CI；(c) 决定 fork 何时彻底脱离上游。

- **Q10. 缺少与现有 Axhub-Make 功能的差异说明**
  proposal 反复说"复用现有能力"，但没列出现有 Axhub-Make 究竟有哪些能力、哪些已被增强替代。新加入者无法判断改动半径。

### 🟢 低

- **Q11. 组件图标、缩略图等设计资产来源未提**（tasks 3.7 提到预览缩略图，但未说谁设计/生成）。
- **Q12. 缺少 i18n / 中英文支持的说明**（Axhub-Make 是中文工具，组件名/属性面板是否需要英文版？）。
- **Q13. 缺少无障碍（a11y）考量**——原型工具自身的可访问性、生成原型的可访问性。

## 二、用户价值问题

### 🔴 高

- **Q14. 核心价值主张不清晰：这是 "AI 原型生成器" 还是 "可视化编辑器"？**
  手动编辑画布的工作量可能占总开发量 50%+，但用户调研依据是什么？如果用户主要痛点是 "AI 生成不准"，那么增强 AI Prompt 或引入示例库可能比造一个简化版 Figma 更划算。需要提供用户访谈/反馈数据支撑手动编辑的优先级。

- **Q15. 与现有成熟工具相比的差异化不足**
  市场上已有：墨刀 AI、即时设计 AI、MasterGo、v0.dev + 手动微调、Penpot。文档未回答："为什么用户要选 axhub-proto-enhanced 而不是 v0 生成 + Figma 微调？" 尤其是 v0/Figma 的手动编辑体验远超自研画布。

### 🟡 中

- **Q16. "混合工作流 AI→手动→再 AI→导出" 是双刃剑**
  "再 AI 优化"这一步若实现不当会抹掉手动修改，反而引起用户不信任。proposal 描述了这条链路但未定义保护机制（diff 预览、版本对比、选择性合并）。这是用户最容易流失的环节。

- **Q17. 静态图片导出的用户价值弱**
  PNG/SVG 导出在浏览器里 `Cmd+Shift+4` 或截图工具就能完成，单独做一个"高清导出"功能 ROI 低。除非用户场景是批量导出上百页，否则建议优先级下调，或用现成库（html-to-image）一行接入而非自建。

- **Q18. 高级组件（图表/地图）建议砍到 v2**
  图表库接入（ECharts/Recharts）+ Axure 映射 + 可编辑保持，工作量接近一个独立项目。如果 v1 用户主要是 PM 做页面布局原型，用占位矩形+文本"图表占位"已足够。建议明确 v1 不包含图表/地图，放入 v2 backlog。

### 🟢 低

- **Q19. 未考虑模板/示例库**——比"高级组件"更能提升 AI 生成质量的方式，是预置 5-10 个常见业务模板（后台列表、表单、详情、Dashboard）。ROI 高但完全未提。

## 三、优先级问题

### 🔴 高

- **Q20. 缺少 MoSCoW / RICE 优先级框架**
  tasks.md 仅按 Phase 1-7 排时间序，但 Phase 内任务（如 3.5 高级组件 vs 3.3 表单组件）无优先级区分。建议给每个功能打 Must / Should / Could / Won't。

- **Q21. 关键路径错位：手动画布应最后做，但 Phase 2 就启动**
  更稳的顺序应该是：
  1. 先扩展组件库 + Axure 导出（Phase 3+4，价值直接、技术风险低）
  2. 再做 HTML/图片导出（Phase 5）
  3. **最后**做手动编辑画布（Phase 2，工作量最大、风险最高、价值假设最未验证）
  当前顺序把最大风险放在最前面，一旦 Phase 2 做不出来，Phase 3-7 全部 blocked。

- **Q22. 缺少 MVP 切片定义**
  v1.0.0 包含 Phase 1-7 全部，没有任何 "最小可发布" 切片。建议明确：MVP = AI 生成 + 增强 Axure 导出 + HTML 导出（不含手动画布）。后续 v1.1 再加手动编辑。

### 🟡 中

- **Q23. 工作量评估缺失**
  tasks.md 无每项任务的工时估算，无关键人力假设（几个人？前端/全栈？）。手动编辑画布单项预计 2-4 周（含撤销重做、对齐吸附、属性面板），未单独标注。

- **Q24. Phase 7"持续集成 GitHub Actions"应在 Phase 1 就建立**
  没有 CI 就没有自动化测试网，前面 Phase 2-6 的回归测试全靠人工，风险大。CI 是基础而非收尾。

- **Q25. tasks.md 4.8 "修复 Axure Bridge 兼容性问题" 排期位置错误**
  这是高风险未知项，应在 Phase 4 开始前 spike 验证，而不是放在 Phase 4 末尾。

### 🟢 低

- **Q26. 缺少文档与示例的并行任务**——文档任务（6.6）堆在 Phase 6，建议每 Phase 完成即更新对应文档。

## 四、汇总：Top 5 必须立即澄清的问题

| # | 问题 | 严重度 | 责任方 |
|---|------|--------|--------|
| 1 | Q3/Q4：手动画布的边界、与 AI 再生成冲突解决、项目数据模型 | 🔴 高 | PM + 架构师 |
| 2 | Q14/Q15：用户调研依据 + 与 v0/Figma 的差异化论证 | 🔴 高 | PM |
| 3 | Q21/Q22：调整 Phase 顺序，定义 MVP 切片（先导出后画布） | 🔴 高 | PM + Tech Lead |
| 4 | Q7：高级组件在 Axure 中的可编辑性降级策略 | 🔴 高 | Tech Lead |
| 5 | Q5：成功标准量化（性能、组件清单、merge 验收指标） | 🔴 高 | PM |

---

**评审结论**：方向有价值（Axure 增强导出确实是 Axhub-Make 短板），但当前文档把最高风险的手动画布模块低估且排前，缺少用户价值论证和 MVP 切片。**建议打回重新拆分：拆成 v1.0（Axure 导出增强 + HTML 导出，2-3 周可交付）和 v1.1（手动编辑画布，需先 spike 验证）。**
