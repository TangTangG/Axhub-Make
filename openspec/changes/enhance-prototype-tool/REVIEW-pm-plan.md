## 建议

### 1. 里程碑调整建议

```
当前：M3(W3) 基础组件 → M4(W4) 表单组件 → M5(W5) 布局组件
建议：M3(W3) 基础组件导出 → M4-M5(W4-5) 表单+布局组件导出（双周并行）
理由：表单和布局组件的 Axure 映射复杂度高于基础组件，单周完成风险大。
```

### 2. 关键路径保障

- **Week 2 末必须完成**：设计 Token 统一（H3）+ 组件接口冻结。若延迟，Week 3-5 全部顺延。
- **Week 3 开始前必须完成**：上游导出机制 Spike（H2）。建议安排 1 名前端 + 1 名后端各 1 天。
- **每周五下午**：里程碑检查会，对照 PLAN.md 验收标准逐项打勾，未达标项立即升级。

### 3. 风险监控机制

| 风险 | 监控频率 | 触发动作 |
|------|---------|---------|
| 上游同步冲突 | 每周 CI 后 | 冲突数 >2 → 架构评审 |
| Axure Bridge 联调阻塞 | 每日站会 | 阻塞 >1 天 → 启动降级策略（剪贴板） |
| 组件导出 L1 可编辑率不达标 | 每周五 | 基础组件 <100% → 暂停新组件，修复映射 |
| 性能不达标（导出 >5s） | 每 Phase 末 | 超限 → 启动优化专项 |

### 4. 进入 Phase 3 的前置条件

- [ ] H1：确认 M4-M5 合并或优先级调整方案
- [ ] H2：完成上游导出机制 Spike，输出分析报告
- [ ] H3：design-tokens.json 与 DESIGN_SPEC.md 字段对齐
- [ ] M1：明确 ≤1px 的适用范围（同浏览器 vs 跨浏览器）
- [ ] M4：定义 E2E 测试环境（Mock Bridge 方案）

## 是否可进入 Phase 3 开发

**有条件可以。**

满足以下条件后即可启动 Phase 1（Week 1）开发：
1. 上述 5 项前置条件全部确认或给出明确解决时间
2. 项目 Kickoff 会上向全员同步本 Review 的风险监控机制
3. 每周五里程碑检查会作为固定议程

**不建议跳过 Phase 1 直接开始 Phase 2**，因为上游同步机制是整个 fork 架构的根基，若 Week 1 未建立，后续所有 Phase 的代码都可能面临上游冲突风险。
