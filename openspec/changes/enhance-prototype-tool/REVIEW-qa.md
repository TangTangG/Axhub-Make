# 需求文档 Review 问题清单 — axhub-proto-enhanced（测试工程师视角）

**Review 角色**：资深测试工程师
**评审对象**：
- `openspec/changes/enhance-prototype-tool/proposal.md`
- `openspec/changes/enhance-prototype-tool/design.md`
- `openspec/changes/enhance-prototype-tool/tasks.md`（参考）

**评审维度**：验收标准可测性 / 边界 Case / 异常处理 / 兼容性测试

---

## 一、Axure 导入的可编辑性验证

### 🔴 高

- **T1. 缺少 Axure 可编辑性的量化验收标准**
  proposal 成功标准 2 仅写"所有组件导出到 Axure 后保持可编辑状态"，但未定义：
  - 可编辑的判定标准是什么？（能修改文本？能调整尺寸？能改样式？能绑定交互事件？）
  - 需要覆盖 Axure RP 哪些版本？（8/9/10/11？）不同版本 widget 模型有差异
  - 表格组件在 Axure 中拆成多少个子 widget？合并单元格场景如何保持可编辑？
  - 缺少"导入后用户操作路径"的验收用例（例如：导入 → 双击文本修改 → 调整下拉选项 → 导出 .rp 重新打开验证）

- **T2. 缺少组件降级策略的可编辑性测试矩阵**
  design.md 提到高级组件（图表/地图/富文本）但 proposal 未说明降级方案。测试需要明确：
  - 图表导出后是变成矩形+文本拼合？还是 Inline Frame？拼合后的各元素是否可独立编辑？
  - 地图组件在 Axure 中无原生对应物，导出后是静态图片还是可交互热区？
  - 富文本的加粗/斜体/列表等格式在 Axure 中是否保持？还是退化为纯文本？
  - 建议输出《组件-Axure 映射可编辑性矩阵》作为测试基准文档

- **T3. Axure Bridge 的异常场景未定义**
  design.md 提到复用 Axure Bridge (localhost:32767)，但缺少：
  - Bridge 未启动时的用户引导流程和错误提示文案
  - Bridge 版本与导出数据格式不匹配时的降级策略
  - 大文件导出时的超时阈值和进度反馈
  - 并发导出多个页面时 Bridge 的队列处理能力

### 🟡 中

- **T4. CSS → Axure 属性映射的边界 Case 未覆盖**
  design.md 提供了 `CSS_TO_AXURE_PROPERTY_MAP`，但测试需要验证：
  - 不支持的 CSS 属性（如 `transform: rotate`、`filter: blur`）的降级策略
  - 百分比/负值/ calc() 等动态值的处理
  - 伪类（:hover/:active）样式如何映射到 Axure 交互样式
  - 继承样式和层叠冲突时的优先级规则

- **T5. 缺少导入后回归测试机制**
  tasks.md 4.7 仅写"测试所有组件在 Axure 中的可编辑性"，但未定义：
  - 自动化测试方案（Axure 是否有 API 可以验证 widget 属性？还是纯人工？）
  - 回归测试频率（每次 merge 上游后？每周？）
  - 测试用例的 Axure 文件版本管理（存放路径、命名规范）

## 二、多模式预览的兼容性测试

### 🔴 高

- **T6. 三种预览模式的一致性未定义**
  proposal 提到 iframe / HTML / 图片三种预览，但缺少：
  - 三种模式下组件渲染是否要求像素级一致？还是允许细微差异？
  - 交互效果在 iframe 和 HTML 导出中是否保持完全一致？（例如：悬停效果、点击跳转）
  - 图片导出时交互组件的静态表现是什么？（悬停状态截哪一帧？）
  - 缺少跨模式一致性测试用例

- **T7. HTML 导出的离线兼容性未定义**
  design.md 提到 `standalone: boolean`（是否独立文件），但测试需要明确：
  - 外部资源（CDN 字体、图片 URL）在离线环境下的降级策略
  - 是否包含 base64 内联图片的阈值（多大图片转 base64？多大保持外链？）
  - 不同浏览器（Chrome/Firefox/Safari/Edge）打开导出 HTML 的兼容性矩阵
  - 移动端浏览器打开导出 HTML 的适配要求

### 🟡 中

- **T8. 图片导出的质量与边界未量化**
  - PNG 导出的 DPI 标准？（72/150/300？）
  - 长页面导出时是单张长图还是分页截图？
  - SVG 导出是否包含外部字体？字体未安装时的 fallback 策略
  - 透明背景组件在 PNG 导出时的底色处理

- **T9. iframe 预览的性能边界未定义**
  - 支持的最大组件数量（100 个？1000 个？）
  - 嵌套层级上限（多少层后性能下降？）
  - 大数据表格（1000 行）的渲染策略（虚拟滚动？分页？）

## 三、上游同步的冲突处理

### 🔴 高

- **T10. 上游同步的验收标准完全缺失**
  proposal 成功标准 5 仅写"保持同步能力"，但未定义：
  - 同步后必须通过哪些测试？（E2E 测试套件？Axure 导出回归测试？）
  - 冲突解决的决策流程文档化（谁决定保留本地还是上游？）
  - 同步失败的回滚策略（如何快速回到上一个稳定版本？）
  - 缺少"上游同步健康度"的量化指标（merge 冲突率、测试通过率）

- **T11. 目录隔离策略的测试覆盖不足**
  design.md 提到 `upstream/` 和 `src/` 目录隔离，但测试需要验证：
  - 构建流程是否正确排除 `upstream/` 的测试文件
  - 本地 `vendor/axhub-export-core` 与上游版本的 diff 追踪机制
  - 禁止修改的上游核心文件清单（design.md 未提供，测试无法验证隔离有效性）

### 🟡 中

- **T12. 缺少上游变更的兼容性预警机制**
  - 上游修改了 `axhub-export-core` 的接口时，本地增强代码如何感知？
  - 是否有自动化脚本检测上游 API 变更对本地代码的影响？
  - 上游 License 变更时的合规检查流程

## 四、通用测试与异常处理

### 🔴 高

- **T13. AI 生成组件树的异常输入未定义**
  - AI 返回非法 JSON / 未知组件类型 / 循环嵌套时的错误处理
  - 组件树过深（>10 层）或组件数过多（>500）时的性能保护
  - AI 生成与手动编辑冲突时的数据一致性保证（design.md 提到"单一数据源"，但未定义并发编辑冲突解决）

- **T14. 手动编辑画布的状态持久化未定义**
  - 画布刷新/关闭后编辑历史是否保留？
  - 撤销/重做的栈深度上限？内存溢出保护？
  - 多人同时编辑（虽然 v1.0 单人，但浏览器多 Tab 场景）的数据竞争处理

- **T15. 缺少端到端测试环境定义**
  tasks.md 6.2 提到 E2E 测试，但未定义：
  - 测试环境的 Axure RP 版本（自动化测试需要真实 Axure 还是 mock Bridge？）
  - 测试数据的准备与清理策略（测试项目文件存放路径）
  - CI 环境中 Axure Bridge 的模拟方案（GitHub Actions 无法运行真实 Axure）

### 🟡 中

- **T16. 性能测试指标完全缺失**
  - 首屏渲染时间（组件树加载 + 画布渲染）
  - AI 生成响应时间（从输入需求到画布可编辑）
  - HTML 导出耗时（单页/批量 10 页）
  - 图片导出耗时（A4 尺寸/全页面）
  - 内存占用上限（大页面编辑时）

- **T17. 缺少浏览器兼容性矩阵**
  - 手动编辑画布支持的浏览器版本（是否兼容 Safari 的 drag-and-drop API？）
  - 不同浏览器的剪贴板 API 差异（复制粘贴组件）
  - 高 DPI 屏幕（Retina）下的画布缩放精度

**评审结论**：当前需求文档在功能层面覆盖了主要场景，但**测试视角的验收标准几乎全部缺失**。特别是 Axure 可编辑性、多模式预览一致性、上游同步健康度这三个核心卖点，均无可量化的验收指标和异常处理定义。建议补充《测试验收标准》文档，明确每个功能的边界 Case、异常路径和量化指标后再进入开发。
