# 需求探索与设计决策指南

用于用户明确要求进入需求探索、需求完善、需求对齐、先写规格、先做方案确认，或使用 `$requirements-exploration` 时，系统化收敛产品需求，再确认设计方案。

普通新建原型、填充占位页、局部修改、bug 修复或用户说“直接生成”时，不自动进入完整需求探索流程。只做必要的轻量澄清：能从上下文判断的自行判断；存在少量阻塞点时一次问清；用户明确授权按假设推进时，记录假设并实现。

核心流程：

```text
读取上下文 -> 判断是否显式进入需求探索 -> 需求探索/轻量澄清 -> 设计基底确认 -> 设计决策确认 -> 规格/计划 -> 实施验证
```

## 何时触发

完整需求探索只在以下情况触发：

- 用户明确说“进入需求探索/需求完善/需求对齐/需求访谈/先对齐需求/先写规格/先做方案确认”。
- 用户使用 `$requirements-exploration`，或从产品界面选择“需求探索”流程。
- 用户要求维护或更新需求探索文档、需求快照或规格文档。
- 当前任务已经处在需求探索会话中，用户继续回答上一轮探索问题。

以下情况默认不触发完整需求探索：

- 新建原型、填充 `untitled-*` 占位页、首页/工作台/系统页面生成。
- 用户需求模糊但表达了“直接生成”“先做出来”“按你理解来”等推进意图。
- 已有原型的局部文案、样式、素材替换、明确 bug 修复。
- 明确的页面补充、功能补齐、交互调整或视觉微调。
- 资料、主题、现有原型或资源目录之间存在小冲突，但可以用合理假设推进并在交付说明中写明。

如果不进入完整需求探索，但问题会显著改变方向、范围、成本或验收标准，可以做轻量澄清。轻量澄清最多聚焦当前阻塞点，不扩展成连续访谈。

## 上下文读取

提问前先读取可获得的信息，不把项目里能找到的问题抛给用户。

优先级：

1. 用户当前消息、附件、截图、链接和已给出的约束。
2. 当前目录最近的 `AGENTS.md`、`README.md` 和相关 `rules/`。
3. 关联原型：目录结构、入口文件、必要样式和已有交互。
4. 资源目录：只做目录级扫描，了解已有原型、主题、文档和资产。
5. 相关文件：只读取会影响本次判断的文件，不批量展开无关文件。

重点看：

- `src/prototypes/`：是否已有同类原型、参考页或可复用页面结构。
- `src/themes/`：是否已有相近主题或设计系统；主题只作为设计基底候选，不作为产品范围来源。
- `src/resources/`：是否已有业务说明、字段、流程资料或素材。
- 原型内 `assets/`、`canvas-assets/`：是否有用户提供或历史沉淀的素材。

## 需求探索

需求探索负责回答“做什么”，方向应以收敛为主。通常需要明确：

- 目标用户和核心任务。
- 本次范围、功能清单和不做什么。
- 页面或资源的核心内容、数据来源和素材来源。
- 关键状态、核心路径和必要交互。
- 用户最终如何判断结果可用。

只问会影响范围、成本或验收的问题。可以推断字段、路径、素材位置、样式延续等细节。进入显式需求探索后，不得推断目标用户、核心任务、产品范围、信息架构、验收标准或设计基底；缺失这些信息时继续提问。

未进入显式需求探索时，可以基于上下文做合理产品假设并推进；但必须在方案摘要或交付说明中写清关键假设。

## 设计方案确认

设计方案阶段负责回答“怎么表达”。进入视觉、主题或明显 UI 改版前，必须先让用户确认一个 `DESIGN.md` 作为设计基底：

1. 如果用户已指定 `DESIGN.md` 或主题，直接采用为设计基底；这不代表产品需求已确认。
2. 如果用户未指定，优先从项目默认主题、已有同类原型和 `src/themes/` 中整理 3-4 个最匹配候选，让用户选择；只有用户明确进入需求探索时，才先完成完整需求探索。
3. 候选说明只写适用理由、主要风格、取舍和预览链接，不替用户决定最终基底。
4. 不自行新建 `DESIGN.md`；没有合适候选时，先询问用户提供设计基底或主题方向。用户要求直接生成时，可采用最接近的已有基底并说明假设。

整理候选时优先读取主题 `theme.json`，用 `tags.*`、`display.distributionTags`、`identity.title*/description*` 和 `display.variant` 做检索与候选说明；这些字段不得用来推断用户要做的业务类型。用 `identity.slug` 和 `assets.designMd.path` 校验目录与 `DESIGN.md` 路径。

候选必须提供可打开的主题预览链接。优先使用资源 metadata 里的 `clientUrl` / `previewUrl`；没有时使用 `/themes/<theme-slug>`。同时标出对应 `DESIGN.md` 路径，便于用户核对。

`DESIGN.md` 确定后，用户零散提出的颜色、字体、布局、动效、组件形态等需求，都作为基于该设计基底的调整处理，不另起一套视觉系统。

新建页面、大面积 UI 改版或模糊需求，设计阶段至少覆盖 5 个会影响实现的设计决策变量；可以合并到方案摘要中一次确认，不要求拆成五轮追问。局部微调、明确 bug 修复或用户已给出完整设计约束时保持轻量。

常见设计问题包括：

- 首屏目标：主操作、信息概览、品牌表达或引导转化。
- 信息层级：哪些内容必须突出，哪些可以折叠或延后。
- 布局模式：看板、列表详情、仪表盘、向导、沉浸页或多步骤流程。
- 交互路径：高频用户效率优先，还是首次用户理解优先。
- 数据呈现：真实数据、文档推断、临时示例数据或空状态优先。
- 视觉语气：严格继承 `DESIGN.md`，还是在其基础上加强某种风格倾向。

落地时优先复用所选 `DESIGN.md` 对应的 CSS Variables、tokens 和组件习惯；缺少 token 时贴近所选基底的视觉语言，并在方案或交付说明中写明假设。

## 提问规则

- 先读上下文；只推断细节，不推断产品范围、信息架构、验收标准或设计基底。
- 普通任务最多询问当前推进所需的阻塞点，不把澄清扩展成完整访谈。
- 显式需求探索默认一次只问一个决策点；同一主题下强相关的 2-3 个参数可以合并为一问。
- 尽量给出 2-3 个互斥选项，并标出推荐答案。
- 推荐答案要说明取舍，不只表达偏好。
- 不为了补齐形式追问已能从上下文判断的细节。
- 用户回答后继续收敛；如果出现新分支，只在显式需求探索中继续追加提问。
- 显式需求探索要粗略统计已回答问题数。每到 50 个问题，提醒用户当前已到一个长会话节点，并让用户选择继续探索、暂停记录当前快照，或进入收尾。
- 用户想停止时，进入收尾：最多再问 5 个高价值问题，优先解决阻塞和验收风险；如果用户要求立即停止，则不再追问。

## 确认与记录

进入实现前需要让用户确认产品需求和设计方案；普通任务可以用轻量方案摘要承载，不要求进入完整需求探索。确认产物可以是中文规格文档、执行计划或方案摘要，但至少包含：

- 产品需求：目标用户、核心任务、范围、功能清单、内容/数据来源、验收重点。
- 设计方案：采用的 `DESIGN.md`、整体设计方向、关键设计决策、设计假设。
- 实施边界：本轮会做什么，不会做什么。

确认过的完整需求探索或规格需要归档为当时决策快照；普通轻量方案默认不归档，除非用户要求、任务风险高，或已经形成可复用规格。归档前必须先确定目标原型；未确定目标原型时不写文件，先让用户选择或创建目标原型。

- 保存位置：所有需求探索、规格快照和设计决策归档都写到 `src/prototypes/<prototype-name>/.spec/`。
- 文件命名：文件名必须包含日期，建议使用 `YYYY-MM-DD-<topic>.md`。
- 归档内容：只记录已确认的需求问题、设计问题、用户选择和最终设计决策。
- 归档性质：只表示当下决策，不要求跟随后续实现继续同步变化。
- 禁止位置：不要写入 `src/resources/requirements/`、根目录 `docs/`、`.axhub/make/` 或任何会话型索引目录。

显式需求探索不每问都写文档，按以下节点记录：

- 每完成 10 个已回答问题，记录一次已确认快照。
- 用户要求暂停、停止、总结、进入实现时，记录一次。
- 探索自然结束时，记录一次。
- 确认重大且不可逆的产品决策时，可即时记录。

触发过完整需求探索时，本轮交付说明或确认产物中只需补充：

- 问题。
- 用户选择。
- 最终设计决策。
