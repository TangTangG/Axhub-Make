# Make 客户端升级保留项目依赖设计

## 背景

当前 Make 客户端升级会把在线模板中的 `package.json` 加入升级写入清单，并通过整文件复制覆盖项目文件。升级虽然会先把原文件备份到 `.axhub/make/backups/client-update-*/original/package.json`，但项目自行添加的依赖、脚本和其他字段仍会从升级后的工作文件中消失。

本设计把 `package.json` 从普通模板文件改为具有明确归属规则的结构化合并文件。官方模板继续控制客户端运行所需的配置，项目自行扩展的内容在不与官方模板冲突时得到保留。

## 目标

- 客户端升级后保留项目独有的依赖和脚本。
- 同名依赖或脚本存在差异时，以新版官方模板为准。
- 保持官方模板对客户端版本、运行方式和基础配置的控制权。
- 在解析或合并失败时，不写入任何项目文件。
- 保留现有升级备份、依赖安装、元数据同步和 API 返回结构。

## 非目标

- 不引入旧模板、当前项目、新模板的三方合并。
- 不提供交互式逐项冲突选择。
- 不修改普通模板文件的覆盖规则。
- 不改变 `src/resources/`、侧边栏状态和项目自有原型的现有保护规则。
- 不识别项目删除官方依赖的意图；只要新版模板仍声明该依赖，升级结果就按模板恢复它。

## 方案选择

采用升级写入前的语义合并方案：先解析项目和模板的 `package.json`，生成唯一的合并结果，再进入备份和写入阶段。

未采用以下方案：

- 先覆盖再从备份补回字段：中间状态不完整，写入或安装失败时更难判断最终状态。
- 三方合并：需要保存每个历史模板基线并引入冲突状态；在“冲突时官方优先”的既定规则下收益不足。

## 合并规则

模板对象是官方基线，项目对象提供非冲突扩展。

### 键级合并字段

以下字段按子键合并：

- `dependencies`
- `devDependencies`
- `peerDependencies`
- `optionalDependencies`
- `scripts`

项目独有依赖先保留在原字段中，再写入全部模板依赖。因此：

- 仅存在于项目中的键保留。
- 仅存在于模板中的键加入结果。
- 双方同名的键使用模板值。
- 只要模板在任一依赖字段中声明了某个包，就先移除项目在全部依赖字段中的同名声明，再按模板指定的字段和版本写入。

因此，如果项目把一个包放在 `devDependencies`，而模板把同名包放在 `dependencies`，最终结果只保留模板的 `dependencies` 声明。模板同时决定官方依赖的版本和依赖类型。`scripts` 不需要跨字段处理，仍按脚本名直接合并。

### 其他顶层字段

其他字段采用浅层合并：

- 项目独有的顶层字段保留。
- 模板独有的顶层字段加入结果。
- 双方同名的顶层字段整体使用模板值。

这意味着 `name`、`version`、`private`、`type`、`packageManager` 等官方模板字段保持官方值；项目独有的工具配置仍可保留。对于 `overrides`、`pnpm` 等未列入键级合并清单的对象，如果模板也提供同名字段，则整个字段以模板为准。

### 输入校验与输出格式

- 两个文件都必须是有效 JSON，且顶层必须是普通对象。
- 键级合并字段存在时必须是普通对象；数组、字符串或 `null` 均视为无效输入。
- 模板缺少 `package.json` 时沿用模板不可用错误。
- 合并结果统一输出为两个空格缩进并以换行结尾的 UTF-8 JSON。
- 合并函数是无副作用的纯函数，不修改任一输入对象。

## 组件与数据流

在 `src/server/makeClientProject.ts` 的客户端升级域内增加一个独立的包清单合并单元。它负责解析、校验、合并和序列化，不负责文件备份、模板下载或执行安装命令。

升级顺序调整为：

1. 下载并解压目标版本模板。
2. 收集模板升级文件清单。
3. 读取并校验项目与模板 `package.json`。
4. 生成合并后的 `package.json` 内容。
5. 创建升级备份，保留项目原始文件内容。
6. 写入普通模板文件，并用预先生成的合并内容写入 `package.json`。
7. 根据包清单变化和依赖安装状态执行 `npm` 或 `pnpm install`。
8. 同步项目元数据并完成升级备份清单。

`package.json` 仍保留在 `plannedFiles` 和 `writtenFiles` 中，因此管理 API 和现有前端无需调整字段结构。

## 写入与失败处理

项目或模板包清单解析失败发生在备份和写入之前。此时升级直接失败，项目目录中的所有文件保持不变，错误阶段标记为包清单合并阶段，并提供可识别的错误代码和文件来源。

合并后的 `package.json` 使用同目录临时文件写入，再通过重命名替换目标文件。这样进程在单次文件写入期间中断时，不会留下截断的 JSON。临时文件在成功或失败后都应清理。

普通模板文件写入失败时沿用现有升级失败与备份上下文。依赖安装失败时沿用当前的成功附带警告行为：合并后的包清单保留，响应包含 `MAKE_CLIENT_INSTALL_FAILED` 等安装阶段信息，用户可在修复环境后重新安装依赖。

## 锁文件策略

模板中的 `pnpm-lock.yaml` 继续按现有升级文件规则写入，随后由依赖安装命令依据合并后的 `package.json` 更新。项目使用 npm 时，现有安装方法选择和 npm 锁文件处理保持不变。

本次不对锁文件进行文本或结构化合并。锁文件由包管理器生成，直接合并容易产生无法安装的依赖图。若安装失败，升级备份仍包含升级计划内原有锁文件，响应同时返回安装警告。

## 测试设计

### 合并单元测试

- 保留项目独有的生产依赖、开发依赖、对等依赖和可选依赖。
- 同名依赖使用模板版本。
- 模板把依赖移动到其他依赖字段时，移除项目中的旧字段声明并采用模板字段。
- 保留项目独有脚本，同名脚本使用模板命令。
- 保留项目独有顶层字段，同名顶层字段使用模板值。
- 不修改输入对象。
- 拒绝无效 JSON、非对象顶层和类型错误的键级合并字段。
- 输出格式稳定并包含末尾换行。

### 升级 API 回归测试

- 包含项目自定义依赖和脚本的客户端升级后仍保留这些字段。
- 官方模板对同名依赖和脚本的更新生效。
- 原始 `package.json` 逐字节保存在升级备份中。
- 无效项目 `package.json` 会阻止升级，模板文件、客户端标记和包清单均未写入。
- 合并结果发生变化时执行依赖安装；依赖安装缺失时仍按现有逻辑执行安装。
- `plannedFiles` 和 `writtenFiles` 继续包含 `package.json`。
- 依赖安装失败时，API 返回升级后警告且合并后的依赖声明仍存在。

## 验收标准

给一个基于旧模板的客户端项目添加模板中不存在的依赖和脚本，再升级到新版模板后：

- 项目独有依赖和脚本仍存在。
- 新版模板新增的依赖和脚本存在。
- 双方同名项与新版模板完全一致。
- 原始包清单可以从升级备份中恢复。
- 依赖安装使用合并后的包清单完成，项目能够继续启动。
