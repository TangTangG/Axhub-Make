# AI 指导中的升级优先与 Bug 报告设计

## 背景

`docs/guide-users-with-axhub-make.md` 已要求 AI 确认用户当前版本和问题状态，但没有明确把版本升级放在所有问题的优先处理位置，也没有说明确认系统缺陷后怎样整理一份可交给 Axhub Make 官方的报告。

默认用户是不了解技术的产品经理或设计师。AI 应承担版本核对、复现、证据整理和报告编写，不应把日志分析或报告组织工作转交给用户。

## 目标

- 明确处理任何问题时都先检查 Axhub Make 和 Make 客户端版本；存在可用更新时优先升级，并在升级后重新验证原操作。
- 对升级后仍存在或已有可靠证据的疑似系统 Bug，生成一份尽可能详尽、可直接提供给 Axhub Make 官方的 Markdown 报告。
- 确保报告的事实边界、环境与版本信息、技术证据和隐私处理正确。

## 升级优先规则

在“工作原则”中增加全局规则：处理任何问题时，先确认 Axhub Make 与当前 Make 客户端是否有可用更新；有新版本时优先升级，再在升级后的版本上重试原操作并继续判断。

在“标准指导流程”中把版本检查和升级放在确认用户目标之后、其他排查之前，使该原则成为明确的执行步骤，而不是背景建议。

升级不是对所有问题的原因结论。AI 仍需记录升级前后的版本和复现结果；升级后问题消失则说明当前结果，升级后仍存在才继续排查或进入 Bug 报告流程。

## Bug 报告触发条件

完成版本检查和优先升级后，如果问题在当前可用版本上仍存在，或虽然不能稳定复现但已有可靠错误与日志证据，就把问题作为疑似系统 Bug 整理报告。不能稳定复现时记录出现频率、最近发生时间和已知触发条件；缺少的事实写明“未确认”，不得猜测根因或把使用方式、环境问题直接断言为系统缺陷。

## 报告内容

报告不强制使用固定模板，可以按问题自由组织，但应尽量保留完整的本地环境和技术细节，方便官方定位。至少包含：

- 一句话问题摘要；
- Axhub Make 版本和 Make 客户端版本；无法确认时明确标记；
- 操作系统版本与架构，以及 Node.js、npm 等相关运行环境版本；
- 浏览器名称与版本，以及与问题直接相关的 Agent/CLI、Axure 或其他第三方软件版本；
- 用户目标和发生问题的页面、入口或功能；
- 最短可复现步骤；
- 实际结果与预期结果，以及问题出现频率和是否可以稳定复现；
- 完整报错文本、浏览器控制台、服务端或客户端日志、相关网络请求和响应；
- 截图、视频、发生时间，以及与问题直接相关且已脱敏的配置或文件片段；
- 已执行的版本升级，以及升级后的复现结果；
- 影响范围和已知临时绕过方式；没有时可以省略。

报告和附件默认保存在项目已忽略的 `.local/` 目录，不提交仓库。交给官方前遮挡账号、项目名称、访问地址、密钥和其他隐私信息。

## 范围

- 实现阶段只修改 `docs/guide-users-with-axhub-make.md`。
- 不创建固定 Bug 报告模板，不规定文件名或官方提交渠道；格式自由不代表省略可取得的环境和技术细节。
- 不修改 FAQ、README、版本升级实现或产品代码。
- 不硬编码当前版本号；AI 必须读取用户实际环境中的版本。

## 验证

- “工作原则”和“标准指导流程”都明确升级优先。
- Bug 报告在升级后问题仍存在，或已有可靠错误与日志证据时生成。
- 报告不猜测根因，并尽量收集完整的本地环境和技术证据。
- 报告最小字段包含 Axhub Make 版本、Make 客户端版本、操作系统与运行环境、相关软件版本、复现步骤、实际/预期结果、错误与日志证据和升级后结果。
- 报告格式自由但内容详尽，临时文件保存在 `.local/` 并要求脱敏。
- `git diff --check` 无空白错误，最终实现提交只包含目标指导文档。
