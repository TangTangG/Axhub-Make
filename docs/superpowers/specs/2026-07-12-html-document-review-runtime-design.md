# HTML Document Review Runtime Design

## Goal

Turn HTML documents under `src/resources/` into a general review surface inside Axhub Make while preserving the current Commentary interaction model.

The first release is Make-only. The design must keep a future standalone integration possible, but it does not need to publish a framework-independent browser SDK yet.

The product is not a second standardized review-list application. The HTML remains the review artifact and owns its content, layout, questions, comparisons, controls, and visual hierarchy. Axhub supplies a small runtime contract for discovering review results, opening editable diagrams, persisting evidence, and submitting feedback through the existing Commentary workflow.

## Product Position

The core product promise is:

> An Agent can generate an ordinary HTML document, and Make automatically turns it into a reviewable artifact without requiring the Agent to generate Axhub UI, resource plumbing, editor integrations, or large feedback payloads.

This direction preserves Agent freedom while reducing generated code, token usage, latency, and integration failures.

## Confirmed Principles

- HTML review content stays inside the HTML document. Make does not create a separate standardized review checklist.
- Page-local feedback is collected before it is sent to an Agent.
- Existing Commentary behavior remains unchanged:
  - an individual item can execute independently;
  - the top-level execute and copy-prompt actions include all pending feedback.
- Standard capabilities are implemented by Axhub, not repeatedly generated by the Agent.
- Do not introduce an Axhub component DSL such as `<axhub-canvas>` or `<axhub-choice>`.
- Ordinary HTML documents do not need React. Make may continue to use React internally in its injected runtime.
- Large files are referenced by project-relative path. Their complete contents must never be embedded into generated prompts.
- Mermaid and Draw.io edits remain durable, editable project assets rather than temporary browser state.

## Version 1 Scope

Version 1 applies only to HTML documents in the active Make project's `src/resources/` tree.

It includes:

1. Existing element and text Commentary on HTML documents.
2. Page-authored interactive review decisions collected through a minimal browser protocol.
3. Automatic recognition of Mermaid and editable Draw.io SVG diagrams.
4. A diagram action inside the existing Commentary card.
5. New-window editing through Make's existing Excalidraw canvas or Draw.io editor.
6. Durable diagram source and preview files beside the HTML document.
7. Diagram feedback returned to the originating HTML Commentary item.
8. Individual execution, global execution, and copy-prompt aggregation.
9. Reference-only prompt generation.

Version 1 does not include:

- arbitrary public websites;
- multi-user reviewer identity or answer merging;
- a separate review-task database or checklist UI;
- automatic reverse conversion from Excalidraw to Mermaid;
- automatic inline HTML rewriting after canvas edits;
- a public standalone browser bundle for `@axhub/commentary`;
- Canvas/SVG chart-library adapters such as ECharts or Plotly;
- automatic layout audits or visual regression reports.

## Existing Foundation

Make already injects `html-template-bootstrap.js` into HTML document previews and exposes the same host-toolbar bridge used by prototype Commentary. A plain HTML resource therefore already works without importing React in the document itself.

The current package boundaries are:

- `@axhub/commentary` owns selection, text and style changes, persistence, prompt composition, task states, and the built-in card UI.
- `@axhub/commentary-react` is only a convenience adapter for React-owned element tweak state. Its underlying tweak protocol is framework-independent.
- Make owns project files, resource routes, Excalidraw, Draw.io, preview windows, Agent execution, and the injected HTML bootstrap.

The first release should extend these boundaries instead of splitting or republishing the packages.

## User Experience

### Opening an HTML document

The user selects an HTML resource in Make and enables the existing “批注” mode. The page remains the primary artifact. There is no additional review-list panel.

The user can:

- select an element and leave a normal Commentary instruction;
- select a text range;
- operate page-authored controls in browse mode;
- make a choice or confirmation that the page records as pending feedback;
- select a Mermaid or Draw.io diagram and open its editor;
- execute one item from its Commentary card;
- execute or copy all pending feedback from the existing host toolbar.

### Interactive decisions

The HTML is free to render radio groups, checkboxes, cards, toggles, comparisons, sliders, tables, or custom controls. Axhub does not impose their layout or schema.

The injected runtime exposes one small, framework-independent API:

```ts
window.axhubReview.setFeedback({
  key: 'checkout-layout',
  element: reviewCardElement,
  title: '结算页布局',
  value: '采用紧凑布局',
  instruction: '将结算页调整为紧凑布局',
  data: { layout: 'compact' },
});
```

The API semantics are:

- calling `setFeedback` records or replaces a pending result;
- it never starts an Agent task by itself;
- `key` replaces an earlier unsent result for the same question;
- `element` associates the result with the page region used by the Commentary card;
- `title`, `value`, and `instruction` are bounded strings suitable for prompt summaries;
- `data` is optional small structured metadata and is size-limited;
- removing or resetting an answer calls `clearFeedback(key)`;
- the runtime persists pending feedback by HTML resource scope and key;
- HTML controls remain responsible for their own visible state.

This is intentionally similar to Lavish's small queue API, but it feeds Commentary's existing local/global actions instead of creating a separate conversation queue.

If the API is unavailable outside Make, the HTML continues to work as an ordinary page. The page must not fail solely because Axhub review integration is absent.

### Commentary integration

Pending interactive feedback behaves as an element-level Commentary contribution:

- the associated card shows the current answer and a pending indicator;
- the card's individual execute action submits only that target's normal comment, decision, and diagram evidence;
- top-level execute and copy-prompt actions include every pending target;
- changing an unsent answer replaces it instead of creating duplicate items;
- successful Agent handling moves the feedback to the existing completed state;
- clear-edits removes pending feedback state but does not delete durable diagram source files.

## Diagram Discovery

Diagram support must use normal Mermaid and Draw.io conventions, not Axhub markup.

### Mermaid

The runtime recognizes:

- source elements with the standard `.mermaid` class;
- rendered Mermaid SVGs identified by Mermaid output markers and a matching source container.

Rendered Mermaid libraries may replace the original DOM text with SVG. For that reason, the Make server parses the raw HTML resource and returns authoritative Mermaid sources in document order. The live runtime uses the rendered DOM only for selection and visual targeting.

Each diagram receives a stable target made from:

- HTML resource path;
- an existing element ID when available;
- otherwise the nearest semantic section ID or heading context;
- document-order diagram index as the final fallback;
- normalized source hash as the version marker.

The Agent is encouraged to use ordinary semantic IDs because they benefit HTML accessibility and review stability, but Axhub-specific attributes are not required.

### Draw.io SVG

The runtime recognizes:

- `<img>`, `<object>`, and links targeting `*.drawio.svg`;
- inline SVG containing standard Draw.io `data-drawio` data;
- inline SVG containing `metadata#drawio-source`.

A plain SVG without embedded Draw.io source is viewable but not structurally editable. It may be opened as a background image in Excalidraw in a later release, but version 1 must not present it as a lossless Draw.io document.

### Selection behavior

When a user selects any child shape, label, or path inside a recognized diagram, Commentary normalizes the tool target to the owning diagram. The existing element selector and normal comment target may remain precise, but the diagram editor action always applies to the complete diagram.

The Commentary card displays “在画布中打开” for Mermaid and “在 Draw.io 中打开” for editable Draw.io SVG.

## Diagram Editing and Round Trip

### Mermaid to Excalidraw

On first open, Make:

1. reads the authoritative Mermaid source from the raw HTML;
2. calculates the normalized source hash;
3. converts the source using the existing Mermaid-to-Excalidraw dependency;
4. saves the converted scene as the baseline;
5. creates a durable `.excalidraw` source file;
6. opens the existing Make canvas in a new window;
7. autosaves edits and refreshes a PNG preview.

Supported Mermaid types produce editable Excalidraw elements with stable node and edge IDs where the converter permits. Unsupported types may open as an image background with drawing and annotation layered above it. The UI must disclose this fallback.

Make does not attempt to convert arbitrary Excalidraw edits back into Mermaid. Freehand marks, layout changes, added shapes, and unsupported constructs make a reliable reverse conversion impossible.

### Draw.io

For an HTML reference to an existing `.drawio.svg`, Make opens and saves that source file directly.

For inline Draw.io SVG, Make extracts the embedded model into the HTML document's supporting-assets directory on first edit. The Draw.io editor saves the extracted source and a PNG preview. The originating HTML is not silently rewritten; the edited file becomes evidence for the Agent to apply to the HTML.

### Feedback return

The diagram editor and originating HTML page communicate through a Make-owned review session, not only through `window.opener`. This allows either window to reload without losing the association.

The returned diagram draft contains metadata, not embedded file contents:

```ts
interface DiagramReviewDraft {
  documentPath: string;
  diagramKey: string;
  diagramKind: 'mermaid' | 'drawio';
  sourceHash: string;
  sourcePath: string;
  previewPath: string;
  summary: {
    added: number;
    removed: number;
    moved: number;
    relabeled: number;
    drawn: number;
    lines: string[];
  };
  updatedAt: number;
}
```

The Commentary card then shows:

- “画布已修改”;
- a short bounded change summary;
- last saved time;
- reopen action;
- existing individual execute action.

### Change summary

Make stores the initial converted scene as a baseline and compares it with the edited scene when prompt evidence is requested. The summary may describe added, removed, moved, resized, relabeled, connected, or freely drawn elements.

The summary is evidence, not a complete serialized patch. It is bounded to counts and at most twelve short lines so prompts stay small.

### Source changes and staleness

The manifest stores the source hash used to create the canvas.

If the HTML Mermaid or inline Draw.io source changes:

- the existing canvas is marked as based on an older source;
- Make never silently merges it with the new source;
- the user may keep reviewing the saved scene or regenerate from the latest source;
- regeneration preserves the older source file as history until the user explicitly removes it;
- feedback always states which source hash the canvas refers to.

## Durable Storage

Diagram review sources are stored beside the HTML document as supporting project assets.

Example:

```text
src/resources/review/checkout-plan.html
src/resources/review/checkout-plan.assets/
├── diagram-manifest.json
├── diagrams/
│   ├── mermaid-order-flow.excalidraw
│   ├── mermaid-order-flow.png
│   ├── drawio-system-arch.drawio.svg
│   └── drawio-system-arch.png
└── history/
    └── mermaid-order-flow-<source-hash>.excalidraw
```

Storage rules:

- editable `.excalidraw` and `.drawio.svg` sources are durable and may be version controlled;
- PNG files are generated preview caches;
- `diagram-manifest.json` is written by Make and maps document targets, source hashes, current source files, and preview files;
- `<html-name>.assets/` is treated as a supporting-assets directory and is not expanded as independent resources in the normal sidebar;
- Agents never need to create or update the manifest;
- clearing comments does not delete diagram assets;
- deleting or moving an HTML document includes an explicit supporting-assets operation;
- server APIs validate every generated path under the selected HTML document's supporting-assets directory.

## Reference-only Prompt Contract

Prompt generation must follow a strict reference-only rule for large or structured files.

Never embed:

- complete HTML documents;
- complete Mermaid source blocks;
- Excalidraw JSON;
- Draw.io XML or SVG;
- PNG or other Base64 data;
- DOM snapshots;
- machine-absolute paths.

Prompts may contain only:

- project-relative document path;
- stable target description and diagram index;
- user instruction or selected answer;
- a bounded change summary;
- project-relative source and preview paths;
- source hash when needed for stale-version safety.

Example:

```text
HTML 文档：src/resources/review/checkout-plan.html
图表定位：Mermaid 图表 2，“退款流程”章节
用户说明：退款失败后增加人工审核节点
画布源文件：src/resources/review/checkout-plan.assets/diagrams/mermaid-refund-flow.excalidraw
预览图：src/resources/review/checkout-plan.assets/diagrams/mermaid-refund-flow.png
修改概览：新增人工审核节点；退款失败分支改接人工审核；审核通过后重新进入退款流程

请读取上述文件并更新原 HTML 中对应的 Mermaid 源码。
```

The Agent reads referenced files only when it needs their details. This rule applies equally to individual execution, global execution, and copy-prompt output.

## Package and Host Responsibilities

### `@axhub/commentary`

Add framework-independent capabilities for:

- review-feedback registration, replacement, clearing, persistence, and snapshots;
- associating feedback with an element target;
- diagram target detection and child-to-owner normalization;
- optional element-card tools supplied by a host;
- diagram draft status and bounded summary display;
- inclusion in individual and global prompt composition;
- cleanup and task-state integration.

The core exposes interfaces and callbacks. It must not import Make APIs, know Make routes, or write workspace files.

### Make host and HTML bootstrap

Make owns:

- raw HTML Mermaid-source extraction;
- Draw.io source extraction;
- diagram identity and manifest APIs;
- creation of durable diagram assets;
- Mermaid-to-Excalidraw conversion orchestration;
- new-window URLs and review-session coordination;
- canvas and Draw.io autosave;
- PNG preview generation;
- project-relative path normalization;
- host callbacks used by Commentary card tools;
- Agent execution and prompt delivery.

### `@axhub/commentary-react`

No version 1 changes are required. React pages may call the framework-independent browser protocol directly. A future helper hook is optional and must not become a prerequisite.

### Default Make client

The default client receives a committed example resource:

```text
client/src/resources/examples/html-review-demo.html
client/src/resources/examples/html-review-demo.assets/
```

The example demonstrates:

- normal element and text Commentary;
- an ordinary Mermaid diagram;
- an editable Draw.io SVG;
- a radio-card decision;
- a multi-select confirmation group;
- replacing a pending answer with the same key;
- individual and global execution behavior;
- graceful behavior when `window.axhubReview` is unavailable;
- source and preview path-only feedback.

The example must remain a plain HTML document with no React application code.

## Error Handling

- Missing Mermaid source: keep normal Commentary available and disable the canvas action with a clear explanation.
- Mermaid conversion failure: allow a visual-background fallback when a rendered SVG is available; otherwise preserve the failure without creating an empty source file.
- Draw.io SVG without an embedded model: explain that the SVG is view-only rather than opening a misleading editor.
- Popup blocked: show a retry action and the editor URL; do not lose the created draft.
- Autosave failure: keep the editor open, show unsaved state, and do not mark the HTML card as updated.
- Missing or deleted supporting file: keep manifest history and offer regeneration.
- Source hash mismatch: mark stale and require an explicit user choice before regeneration.
- Invalid or escaping file path: reject the request server-side.
- Runtime API unavailable: page controls continue to work and no uncaught exception is produced.
- Oversized interactive feedback data: reject or truncate with a visible warning before it reaches prompt composition.

## Security Boundaries

- HTML-originated messages cannot choose arbitrary write paths.
- The server derives output paths from the active project, selected HTML resource, and validated diagram key.
- New-window review sessions use opaque IDs and validate the active project and resource on every operation.
- Cross-window messages are origin-checked; durable state remains on the server.
- External links found in Mermaid or Draw.io content use the existing safe-link confirmation behavior.
- Prompt output never exposes absolute workspace paths.

## Product Success Criteria

Version 1 is successful when:

- an Agent can generate a normal HTML review document without importing Axhub packages;
- a non-React HTML page can participate in Commentary review;
- page-authored choices remain fully custom while their final results appear in existing local/global submission actions;
- selecting a Mermaid child exposes a canvas action in the existing card;
- Mermaid edits survive reload and return as path-referenced evidence;
- editable Draw.io SVG opens in the existing Draw.io editor and returns to the same HTML target;
- no prompt contains full diagram files, Base64 assets, DOM snapshots, or absolute paths;
- stale source changes are visible and never silently merged;
- the default client example demonstrates the entire workflow.

## Rollout and Product Signals

The example page is the primary first-run teaching surface. It should explain the workflow through normal page content and visible controls, without requiring users to read an integration manual before trying it.

Make may record local product events for:

- HTML review mode entered;
- interactive feedback registered;
- individual or global feedback submitted;
- diagram editor opened;
- diagram draft returned successfully;
- prompt rejected by the reference-only guard;
- stale diagram detected.

Useful release signals are time from opening the example to the first submitted item, diagram open-to-return success rate, average generated prompt size, and the share of generated HTML documents that work without manual integration repair. Event data must not include review answers, HTML contents, diagram contents, file contents, or absolute paths.

## Verification Strategy

### Commentary package

- review-feedback store registration, replacement, clearing, scope, and persistence tests;
- individual versus global snapshot and prompt tests;
- diagram owner detection from child Mermaid and Draw.io SVG nodes;
- host card-tool rendering and action tests;
- bounded prompt and prohibited-content regression tests.

### Make server and host

- raw Mermaid extraction after client-side rendering has replaced DOM content;
- Draw.io metadata extraction from both supported encodings;
- safe asset-path derivation and traversal rejection;
- manifest create, update, stale detection, move, and deletion behavior;
- cross-window review-session recovery after either window reloads;
- source and PNG persistence;
- path-only prompt generation.

### Default client

- the example is present in the resource tree;
- it loads as a plain HTML document;
- its controls work without the review runtime;
- with Make injection, decisions register and replace correctly;
- Mermaid and Draw.io actions open their editors;
- individual and global prompt output contains relative paths only.

### Browser verification

Run the default client in Make and complete one end-to-end pass:

1. open the example HTML;
2. add a normal element comment;
3. change an interactive decision twice and confirm only the latest result remains;
4. open Mermaid in a new canvas window, modify it, and return;
5. open Draw.io SVG, modify it, and return;
6. execute one diagram item;
7. copy the global prompt;
8. inspect the prompt for relative paths and absence of embedded file content;
9. modify the Mermaid source and verify stale-state handling.

## Later Opportunities

After the Make-only workflow is stable, future versions may add:

- a standalone browser bundle and host adapter for arbitrary HTML;
- layout overflow and clipping audits;
- SVG-series and Canvas chart-library adapters;
- multi-reviewer identity and answer comparison;
- review reports and version-to-version decision history;
- share-link review without a local Make workspace;
- optional React/Vue helpers built on the same framework-independent protocol.

These additions must preserve the first-release principle: the HTML remains free-form, while Axhub owns standard review infrastructure.
