# Plan PRDs 技能设计

## 目标

为 Make Client 新增 `plan-prds` 技能，将用户口述、产品链接、页面截图、PDF、Office 文档、在线文档、Axure 原型和其他资料整理成可追溯的产品上下文，再规划多篇模块化 PRD。

技能覆盖两类任务：

- 已有产品反推：依据能够读取和观察到的事实还原需求，不把推测、行业惯例或改进建议写成既有能力。
- 新产品创作：先确认会影响产品方向的核心需求，再用公开互联网资料补充领域知识和候选方案；外部研究结论必须标为建议或待确认项，不能自动成为用户需求。

混合任务按内容分别执行两种规则：已有部分保持事实约束，新增部分保持研究、建议和用户确认链路。

## 技能边界

`plan-prds` 负责：

1. 索取、读取、采集和登记来源。
2. 建立产品总入口和来源清单。
3. 按产品功能模块拆分 PRD 任务。
4. 维护确认项、任务状态、依赖和分期。
5. 用户确认后，使用 `write-prd` 完成各模块 PRD，或为后续对话生成明确执行入口。

## 存储结构

每个产品使用独立目录：

```text
src/resources/prd/<product-id>/
├── PROJECT.md
├── SOURCES.md
├── PLAN.md
├── sources/
│   ├── web/
│   ├── images/
│   └── documents/
├── prd-01-<module-id>.md
├── prd-02-<module-id>.md
└── ...
```

`<product-id>` 使用小写字母、数字和连字符。处理另一个产品时创建新的 `<product-id>` 目录，不覆盖已有产品资料。重新处理已有产品时，优先读取并增量更新现有控制文档和素材。

## 文档职责

### PROJECT.md

`PROJECT.md` 是产品总入口，也是后续 Agent 首先读取的文件。它包含：

- 产品名称和一句话定位。
- 产品背景、目标用户、核心场景、目标和范围边界。
- 已确认事实、关键假设和当前开放问题。
- `SOURCES.md`、`PLAN.md` 和各模块 PRD 的相对路径目录。
- 重要产品决策。

`PROJECT.md` 只保留跨模块且长期有效的信息。详细证据放入 `SOURCES.md`，详细执行状态放入 `PLAN.md`，模块规则放入对应 PRD，避免在四处复制同一正文。

### SOURCES.md

`SOURCES.md` 是来源、证据和采集范围的事实清单。每项来源使用稳定编号，例如 `src-001`，并记录：

- 来源类型、原始位置、访问时间和访问条件。
- 本地保存路径、处理状态、覆盖范围和已知缺口。
- 来源支持哪些产品事实、模块或待确认项。
- 内容属性：`已观察事实`、`合理推断`、`外部研究` 或 `待用户确认`。

网站来源还需要维护页面架构表，至少对应页面名称、路由或进入路径、核心状态、关键交互、截图路径和采集状态。无法枚举的动态内容需要记录采集边界，不能用“已采集全部页面”掩盖遗漏。

### PLAN.md

`PLAN.md` 是多篇 PRD 的执行计划和唯一详细状态来源。每项任务包含：

- 阶段、任务编号、功能模块和目标 PRD 路径。
- 目标、范围和不在本篇处理的内容。
- 使用的来源编号、截图或文档路径。
- 编写前需要用户确认的核心问题。
- 依赖任务、建议执行方式和状态。

任务状态固定为：

```text
待确认 -> 待编写 -> 编写中 -> 待评审 -> 已完成
                         \-> 阻塞
```

任务状态变化后只更新 `PLAN.md`；新增、移除或重命名模块 PRD 时同步更新 `PROJECT.md` 的文档目录。

## 统一命名

命名需要稳定、可排序并表达业务含义：

| 对象 | 格式 | 示例 |
| --- | --- | --- |
| 产品目录 | `<product-id>` | `warehouse-management` |
| 来源编号 | `src-<三位序号>` | `src-003` |
| 模块 PRD | `prd-<两位序号>-<module-id>.md` | `prd-02-inventory-transfer.md` |
| 网站截图 | `<三位序号>-<page-id>-<state-id>-<viewport>.png` | `020-login-error-desktop.png` |
| 图片资料 | `<三位序号>-<subject>.<ext>` | `010-order-flow.png` |
| 文档资料 | `<三位序号>-<semantic-name>.<ext>` | `030-business-rules.pdf` |
| 文档提取结果 | `<原文件名去扩展名>.extracted.md` | `030-business-rules.extracted.md` |

同一来源更新时保留来源编号。时间戳或随机字符串不能作为主要文件名；确实需要保留多次采集结果时，在语义名称后增加稳定版本或日期，例如 `020-dashboard-default-desktop-2026-07-17.png`。

## 来源处理

| 来源 | 处理方式 | 主要产物 |
| --- | --- | --- |
| 公开网站 | 使用可用的 Browser、Playwright 或浏览器自动化能力，枚举页面和关键交互状态 | 页面架构、页面截图、交互说明、采集边界 |
| 登录后网站 | 优先使用 Chrome CDP 或 Bridge 复用用户登录状态；不索取或持久化用户密码 | 登录态页面目录、截图和状态说明 |
| 用户截图或图片 | 使用图像读取和分析能力；保留原图或明确引用原路径 | 图片索引、可观察内容和对应模块 |
| PDF、DOCX、PPTX、表格 | 使用当前运行环境内置的对应文档能力读取，必要时保存提取文本 | 原文件索引、提取结果和引用范围 |
| Axure | 使用 `extract-axure-data`，来源为 `https://github.com/lintendo/Axhub-Skills/tree/main/skills/extract-axure-data` | 页面、截图、交互、标注和结构化提取结果 |
| 飞书文档和多维表格 | 使用 `https://www.skills.sh/larksuite/cli` 提供的能力；需要授权时让用户完成授权 | 在线文档或表格内容、字段和来源链接 |
| 其他在线文档 | 使用能够保持原始结构和引用关系的读取方式 | 文本提取、章节索引和原始链接 |

无法访问、解析失败、授权不足或来源互相冲突时，在 `SOURCES.md` 中标为缺口或冲突，并在 `PROJECT.md` 或 `PLAN.md` 中暴露会影响范围的待确认项。不得静默跳过。

## 工作流程

### 1. 确认产品和编制方式

确认 `<product-id>`，检查 `src/resources/prd/<product-id>/` 是否已经存在，并判断本次 PRD 编制属于已有产品反推、新产品创作或混合方式。编制方式用于约束证据和研究规则，不写入 `PROJECT.md` 的产品信息。

### 2. 索取核心资料

向用户索取现有材料，包括口述需求、产品链接、截图、PDF、Office 文件、在线文档和原型链接。只追问会改变产品定位、核心用户、范围或验收方式的问题，不在规划阶段展开页面细节访谈。

### 3. 采集并登记来源

按来源处理表读取资料，统一命名并保存需要长期复用的产物。先完善 `SOURCES.md`，再规划 PRD。已有来源能够复用时不重复抓取；需要回归时使用清单定位原页面、状态和素材。

### 4. 建立总入口和计划

根据已确认事实建立 `PROJECT.md`，再按业务能力而不是页面数量拆分 `PLAN.md`。每篇 PRD 必须能说明目标、边界、引用来源、开放问题和目标路径。

来源缺口会改变模块边界时，先让用户确认采集范围；缺口不影响拆分时可以继续，但必须在计划中显式记录。

### 5. 用户确认

在编写模块 PRD 前，向用户提供 `PROJECT.md`、`SOURCES.md` 和 `PLAN.md` 的路径与预览入口，请用户确认：

- 产品总信息和范围。
- 采集范围、来源缺口和事实/推断分类。
- 模块拆分、分期、待确认项和输出路径。

确认前不批量执行 `write-prd`。

### 6. 分期执行

用户确认后按 `PLAN.md` 顺序执行：

- 上下文充足且任务连续时，在当前对话完成当前阶段。
- 上下文已经较大时，建议每期新开一个对话，并在 `PLAN.md` 中给出该期任务和需要读取的相对路径。
- 默认每期安排 1 至 3 篇 PRD；根据来源数量、模块耦合和文档复杂度调整。
- 相互独立且运行环境支持时，可以使用子代理分别处理；每个任务必须有独立目标路径和来源集合，最终统一更新状态。
- 每篇使用 `write-prd` 编写，完成后进入 `待评审`；确认通过后改为 `已完成`。

## 事实与创作规则

### 已有产品反推

- 只把页面、交互、文案、文档或用户说明能够证明的内容写成事实。
- 行业惯例、可能存在的后台逻辑和未观察状态只能写成推断或待确认项。
- 页面无法访问或交互无法完成时，记录证据缺口，不补写“合理功能”。
- 建议和现状分开；改进建议不能混入反推 PRD 的当前能力描述。

### 新产品创作

- 先确认产品目标、核心用户、关键场景、范围和成功标准。
- 可以搜索公开资料补充领域术语、常见流程、风险、合规和竞品模式。
- 每个外部结论记录链接、访问时间和用途。
- 研究结果作为候选方案或待确认项；只有用户确认后才进入正式范围。

## 技能文件设计

在 Make Client 的 `.agents/skills/plan-prds/` 和 `.claude/skills/plan-prds/` 中保持一致内容：

```text
plan-prds/
├── SKILL.md
├── agents/openai.yaml
├── references/source-handlers.md
└── assets/
    ├── PROJECT.md
    ├── SOURCES.md
    └── PLAN.md
```

`SKILL.md` 保留触发条件、核心规则和阶段流程；特殊来源处理细节放在 `references/source-handlers.md`；三份稳定文档骨架放在 `assets/`，由技能按产品实际内容创建，不保留未替换的模板占位符。

## 验证策略

先在没有新技能指导的情况下运行基线场景，确认一般 Agent 容易出现的失败：跳过来源清单、把推断写成事实、文件命名混乱、直接编写单篇大 PRD或未确认就批量执行。然后使用技能验证以下场景：

1. 已有登录产品链接：能先建立页面和截图索引，不虚构无法访问页面。
2. 只有若干产品截图：能统一命名、登记证据并暴露覆盖缺口。
3. 新产品简述：能询问核心需求、使用公开研究补充，但不把研究建议冒充用户决定。
4. Axure、飞书、PDF 和 Office 混合输入：能选择正确处理入口并记录产物。
5. 已有产品目录：能复用 `SOURCES.md` 和素材，增量更新而非重复采集。
6. 多模块长任务：能生成分期计划、控制每期规模并给后续对话明确入口。

最后校验两个技能目录一致、YAML 和目录命名合法、模板没有 `TODO`、`TBD` 或未解释占位符，并检查 `git diff --check`。

## 完成标准

- `plan-prds` 能在 Make Client 的 Codex/通用 Agent 与 Claude 技能目录中被发现。
- 默认使用 `src/resources/prd/<product-id>/PROJECT.md` 作为产品总入口。
- 三份控制文档职责清楚，路径和状态可追溯。
- 所有落盘素材遵循统一语义命名，并在 `SOURCES.md` 中可定位。
- 反推模式不虚构事实，创作模式保留研究来源和用户确认门槛。
- 用户确认后才批量进入 `write-prd`，且支持分期、续接对话和独立任务并行。
